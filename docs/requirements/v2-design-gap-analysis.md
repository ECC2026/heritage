# 新版《非遗平台一级二级》设计差距分析与迁移计划

> 文档状态：新版页面规格迁移设计基线，不代表功能已经实现。  
> 新版依据：甲方文件《非遗平台一级二级(1).doc》，文件修改时间为 2026-08-10。  
> 现状基线：`heritage-platform` 当前工作区，核对日期为 2026-08-11。  
> 本轮边界：只分析页面、领域模型、API 和运营后台影响；不修改业务代码、数据库或 API。  
> AI 边界：只预留页面点位、路由参数和未来扩展边界，不实现 AI 数字人、语音问答、讲解、长按唤起或素材管理。

## 1. 结论摘要

新版不是对旧页面做文案替换，而是一次信息架构和业务分类轴的调整：

1. 一级 Tab 从“首页 / 非遗 / 商城 / 活动 / 我的”改为“首页 / 分类 / 传承人 / 活动 / 我的”。当前配置证据见 `client_code/pages.json:136-170`、`client_code/custom-tab-bar/index.js:6-31` 和 `client_code/components/bottom-nav.vue:32-62`。
2. 商城仍是必要业务能力，但不再占据一级 Tab；现有 `/pages/shop/list`、商品详情、购物车和订单路由应保留，并从“分类”、首页“购买好物”等入口进入。
3. 传承人从当前首页推荐区和“非遗发现”子频道升级为一级 Tab。当前没有独立传承人列表和详情路由，现有公开接口还存在返回原始实体的隐私风险，因此不能只增加一个 Tab 文案。
4. 当前六大非遗门类是文化名录分类，当前实现为 `category.biz_type='HERITAGE'`，必须保留。新版六大产品体系是面向用户的商品/体验/服务运营分类，必须使用独立 `product_system`；具体服务能力再使用独立 `service_system`。
5. 新版“分类”页是异构业务目录，不是原商城商品分类页。它需要同时聚合商品、课程/体验、康养服务和民俗演艺，并按目标类型跳转到不同详情页。
6. 当前非遗发现、种草社区、知识和资讯没有被新版明确否定，不能删除；建议作为二级内容能力保留、下沉或合并，等待甲方确认最终入口。
7. B 端合作是新增完整业务链路。当前 C 端、后端、SQL 和管理后台均无合作意向对象、页面或接口，必须新建“合作介绍 → 合作表单 → 后台线索处理”的闭环。
8. 首页、活动列表、商品详情的现有视觉和基础交互可复用，但首页聚合 DTO、活动分类字段、商品规格、传承人公开档案和 B 端数据模型仍有明显缺口。

## 2. 新旧规格与当前实现证据

  5. 非遗康养陪伴服务；

## 3. 一级导航迁移分析

| 位置 | 当前 | 新版 | 推荐处置 | 路由策略 |
|---|---|---|---|---|
| Tab 1 | 首页 | 首页 | 保留并重构内容编排 | 继续 `/pages/index/index` |
| Tab 2 | 非遗 | 分类 | 新建产品体系分类页；当前非遗发现页下沉 | 建议新增 `/pages/category/index`，不要覆盖删除 `/pages/community/index` |
| Tab 3 | 商城 | 传承人 | 新建传承人列表；商城下沉 | 建议新增 `/pages/inheritor/list`；保留 `/pages/shop/list` 作为二级页 |
| Tab 4 | 活动 | 活动 | 保留并增强筛选 | 继续 `/pages/activity/list` |
| Tab 5 | 我的 | 我的 | 保留并补齐咨询/消息等入口 | 继续 `/pages/profile/index` |

### 3.1 导航切换原则

1. 先冻结新路由与回退规则，再实施页面；不能先把 Tab 指到不存在或无数据的页面。
2. `/pages/community/index`、`/pages/shop/list` 等旧链接必须保留兼容，避免历史分享、收藏和二维码失效。
3. 后续实施时必须同步修改 `pages.json`、`custom-tab-bar/index.js`、`components/bottom-nav.vue` 和各一级页的高亮 key，不能只改其中一个。
4. 商城从 Tab 移除不等于删除商城。分类页的文创、美食、器具体系以及首页“购买好物”都应进入现有商城列表或对应筛选结果。
5. 传承人 Tab 上线前，必须先完成公开 DTO 脱敏、列表查询和详情查询；不得把现有偏管理用途的 `Inheritor` 实体直接展示到 C 端。
6. 新规格提到中间“+”长按唤起 AI，但同时又把第三个 Tab 定义为传承人。当前阶段第三个 Tab 按“传承人”正常导航实现，只预留未来事件钩子，不实现长按 AI。

## 4. 分类概念边界

### 4.1 三条分类轴必须分开

| 分类轴 | 业务含义 | 当前实现 | 新版处置 |
|---|---|---|---|
| 非遗门类（逻辑 `heritage_category`） | 描述非遗项目属于传统美术、传统技艺等哪种文化门类 | 当前物理实现为 `category.biz_type='HERITAGE'`，由 `/api/heritage-categories` 返回 | **完整保留**，继续服务项目、传承人和知识筛选 |
| 商品分类（product category） | 描述商品运营目录 | 当前也使用 `category`，旧数据默认为 `biz_type='PRODUCT'` | 保留，用于商城内部二级/三级分类，不替代产品体系 |
| 六大产品体系（`product_system`） | 面向用户组织商品、体验、康养、演艺等跨域内容 | 当前不存在 | 新增独立字典和内容映射 |
| 服务体系（`service_system`） | 描述传承人/机构可提供的售卖、定制、教学、上门、康养、演艺、B 端合作能力 | 当前只有 `skillType`、课程 `service_mode` 等零散字段 | 新增独立字典和服务供给关系 |

说明：现有版本化 SQL 中没有物理表名 `heritage_category`；`heritage_category` 是当前 API 和业务逻辑资源名，物理数据位于 `category` 的 `HERITAGE` 域，证据见 `V002__phase1_home_foundation.sql:36-90` 和 `HomeMapper.xml:46-57`。新版迁移必须保留这些数据和 `/api/heritage-categories` 契约。若实际开发库另有未纳入仓库的 `heritage_category` 表，实施前需要只读核对 schema，不能再创建同义重复表。

### 4.2 六大产品体系建议编码

| 稳定编码（建议） | 新版名称 | 当前可关联对象 | 当前成熟度 |
|---|---|---|---|
| `CULTURAL_CREATIVE` | 非遗文创雅物 | `product` | 有基础商品闭环，需补体系映射和规格 |
| `HERITAGE_FOOD` | 非遗美食风物 | `product` | 有商品基础，无食品资质关系和专门筛选 |
| `HERITAGE_UTENSIL` | 非遗器具器物 | `product` | 可复用商品，无产品体系标识 |
| `HANDCRAFT_EXPERIENCE` | 非遗手作体验活动 | `course/course_session`、部分 `activity` | 有首页展示和普通活动，缺课程完整预约 |
| `WELLNESS_COMPANION` | 非遗康养陪伴服务 | 无 | 必须新增服务供给模型 |
| `FOLK_PERFORMANCE` | 非遗民俗演艺 | `performance`、部分 `activity` | 有后端和后台 CRUD，缺 C 端入口和体系映射 |

编码需要甲方确认后冻结；显示名称可以运营配置，但代码和关联关系不能依赖中文名称。

### 4.3 推荐数据结构方向

本轮不执行建表，后续迁移建议为：

- `product_system`：稳定编码、显示名称、简介、图标、封面、排序、状态。
- `product_system_product`：体系与商品的多对多关系。
- `product_system_course`：体系与课程的多对多关系。
- `product_system_activity`：体系与活动的多对多关系。
- `product_system_performance`：体系与演出的多对多关系。
- `service_system`：稳定编码、服务名称、适用主体、说明、排序、状态。
- `inheritor_service_system`：传承人与服务能力关系，可附审核状态、服务城市和简介。
- 后续如需可售/可预约的统一服务产品，再设计 `service_offering`；不要在产品体系基础迁移中一次性引入未确认的交易模型。

不建议把 `product_system_id` 写进 `heritage_category`，也不建议用六个中文字符串覆盖 `heritage_project.category/category_id`。两个维度需要允许多对多组合，例如“传统技艺”项目可以同时产生“文创雅物”“器具器物”和“手作体验”。

## 6. 重点模块详细分析

### 6.1 首页

**当前实现**

- `pages/index/index.vue` 已实现城市、搜索、Banner、六大非遗分类、权威项目、传承人、手作、商品、活动和资讯。
- `GET /api/home` 由 `HomeService#buildHome` 聚合；`HomeResponse` 当前没有 `productSystems`、`coreEntries` 或 `b2bEntry`。
- 首页分类来自 `HomeMapper#selectHeritageCategories`，其 SQL 固定查询 `biz_type='HERITAGE'`，不能直接改名成产品体系。

**迁移建议**

1. 保留城市、搜索和 Banner。
2. “六大非遗分类”移入“发现项目/非遗名录”等二级入口，首页对应位置改为六大产品体系。
3. 新增核心业务入口，但入口目标必须是有效路由：发现项目、认识传承人、购买好物、预约体验/定制服务、B 端合作。
4. 首页热门传承人、推荐商品、课程、活动可以继续作为运营推荐区；资讯是否继续留首页由甲方确认，默认保留在靠后位置。
5. 首页 API 继续采用聚合方式，不退回多个接口并发。新版 DTO 应按区块容错，某个产品体系没有数据时返回空数组而不是整页失败。

### 6.2 六大产品体系

**当前可映射能力**

- 文创雅物、美食风物、器具器物：可由 `product` 起步，但当前 `category` 只能表达商品分类，不表达跨域产品体系。
- 手作体验活动：可复用 `course/course_session` 和普通 `activity/signup`，但两者业务语义必须继续分开。
- 民俗演艺：可复用 `performance` 后端和管理后台，需补 C 端公开查询和体系映射。
- 康养陪伴：无任何正式对象，不能用活动或商品硬凑。

**迁移建议**

- 产品体系是一级运营目录；非遗门类是内容属性；服务体系是供给能力。三者可以交叉筛选，但不能相互覆盖。
- 分类页统一卡片 DTO 至少需要 `targetType,targetId,title,cover,summary,priceText,actionType,actionText`；真实交易仍由商品、课程、活动或演出各自接口完成。
- 不建立“万能业务表”承载所有交易字段。聚合查询可以统一，领域交易模型必须保持独立。

### 6.3 核心业务入口

新版原文存在“认识传人”重复和“B 端端合作”笔误，入口数量、最终文案与卡片组合需甲方确认。建议先按以下五个目标冻结路由：

1. 发现项目 → 当前非遗发现页的“项目”能力或未来项目列表；
2. 认识传承人 → 新传承人一级页；
3. 购买好物 → 商城列表或指定产品体系；
4. 预约体验 / 定制服务 → 课程/服务体系入口；
5. B 端合作 → 合作介绍页。

入口配置应返回 `key,title,subtitle,icon,targetType,targetValue,enabled,sort`，未完成的目标必须显示“筹备中”或不下发，不能点击后白屏。

### 6.4 分类页

分类页不是“六大非遗门类筛选页”，而是六大产品体系的综合目录。

**建议页面结构**

- 顶部：六大产品体系横向/宫格导航。
- 筛选：根据体系动态显示地域、价格、服务方式、日期等；不要求所有体系共用相同筛选字段。
- 内容：商品、课程、活动、演出、服务供给的异构卡片。
- 跳转：商品进入商品详情；课程进入课程详情；活动进入活动详情；演出进入演出详情；康养服务进入服务详情或咨询表单。
- 旧商城入口：保留 `/pages/shop/list`，由文创、美食、器具体系跳入带筛选参数的商城列表。

### 6.5 传承人页

**当前缺口**

- `pages.json` 没有传承人列表/详情。
- `HomeResponse.inheritors` 只有 `id,displayName,portrait,profile,skillType,regionCode`，无法覆盖作品、荣誉、擅长技艺、服务和预约。
- `InheritorController#getInheritors/getInheritorById` 直接返回 `Inheritor`，实体含 `phone/idCard/certificate`，不能用于公开一级页。

**迁移前置**

1. 建立 Public List DTO 和 Public Detail DTO，只返回审核通过、启用且公开展示的档案。
2. 保留证件原文件的私有访问；C 端只返回资质类型、等级、机构、有效期和脱敏摘要。
3. 建立传承人与非遗项目、作品、商品、课程、服务体系的关系。
4. 列表支持地区、非遗门类、级别、服务能力筛选；筛选中的“非遗门类”继续使用现有 heritage category。

### 6.6 活动页

现有活动列表和详情链路可继续复用，但新版需要“市集、手作体验、民俗演艺”和时间、地点筛选。

- 当前 `Activity.type` 是 `Integer`，没有枚举或说明；不得根据 0/1 猜测活动类型。
- 手作课程应使用 `course/course_session/reservation`，普通市集/公益活动继续使用 `activity/signup`，民俗演艺可以复用 `performance`。
- 页面可以在视觉上聚合近期活动，但 API DTO 必须包含明确 `contentType`，详情跳转不能全部假设为 activity。
- 报名仍需按既有一期设计补事务、原子名额和幂等；本次页面迁移不能掩盖该风险。

### 6.7 我的

可直接保留个人资料、订单、报名、帖子、收藏和传承人认证。新版新增“我的咨询、消息通知”，当前无对应路由、表或 API。

推荐分组：

- 交易与履约：订单、预约/报名、售后；
- 内容与关系：收藏、关注、种草；
- 服务与沟通：咨询、消息；
- 身份与合作：传承人认证、B 端合作记录（若允许登录后查询）。

旧“我的帖子”不要因新版未列出而删除，应先改用“我的种草”展示文案或继续保留，等待甲方确认。

### 6.8 B 端合作

当前四端均无实现，属于从零建立的新闭环。

**二级合作介绍页**

- 文旅合作；
- 企业礼品/批量采购与定制；
- 团建手作、活动落地；
- 传承人/服务资源介绍；
- 合作流程、服务范围和表单入口。

**三级合作表单建议字段**

- 合作主体：企业/政府文旅/社区/学校/机构；
- 企业/单位名称、统一社会信用代码（可选，需确认）；
- 合作类型；
- 礼品品类或服务需求；
- 采购数量、预算区间、期望交付周期；
- 城市和落地场地；
- 联系人、手机号、邮箱；
- 需求描述和附件；
- 隐私政策同意、来源渠道、幂等提交 token。

手机号、企业联系人和附件属于敏感数据。公开提交接口需要限流、验证码/风控、幂等；管理后台默认脱敏展示并记录查看与导出审计。

### 6.9 商品详情

现有页面已经具备图片、基础文化类别、描述、数量、收藏、加购和购买，可作为新版详情视觉基础，证据见 `client_code/pages/shop/detail.vue:21-209`。

新版仍缺：

- 视频；
- SKU/规格选择；
- 关联非遗项目；
- 关联传承人；
- 制作工艺/作品故事；
- 食品资质摘要；
- 不同产品体系标签。

新增区块必须由 API 真实字段驱动，字段为空则整个模块不显示。不能在页面中硬编码“国家级非遗”或虚构传承人关系。

### 6.10 传承人详情

建议三级页包含：

- 公开大图、姓名、地区、非遗项目、擅长技艺；
- 资质/荣誉脱敏摘要；
- 作品图文/视频；
- 可售商品；
- 可预约课程、康养或定制服务；
- 关注、预约/咨询入口。

“在线咨询客服”当前无消息系统，首版可进入受控咨询表单或平台客服入口，不能假装已有即时聊天。

### 6.11 活动详情

现有详情页可复用活动海报、介绍、时间地点、收藏、报名状态和报名按钮。后续需要：

- 明确活动类型和组织方；
- 报名开始/结束时间、规则和剩余名额；
- 城市与详细地址；
- `contentType` 区分普通活动、课程和演出；
- 统一错误、空数据和重复提交状态。

活动详情不应因新版分类页引流而修改现有报名业务含义。

### 6.12 B 端合作表单

表单提交后应返回 `leadNo,status,submittedAt`，前端展示成功凭证。管理后台需要状态机：待联系、已联系、方案中、已成交、暂缓、关闭；状态值和可执行动作必须由后端控制。

本阶段不实现对公支付、合同签署、发票或自动匹配传承人，只为后续链路保留需求字段和关联位置。

## 9. API 影响与兼容策略

### 9.1 可继续复用或改造

| API | 处置 | 新版用途 |
|---|---|---|
| `GET /api/home` | 改造 | 新版首页聚合；保留现有字段兼容期，新增产品体系和核心入口 |
| `GET /api/search` | 改造 | 继续搜索项目、传承人、商品、课程，后续扩服务和演出 |
| `GET /api/heritage-categories` | **保留** | 只表示非遗门类，不改造成产品体系接口 |
| `GET /api/heritage-levels` | 保留 | 传承人和项目筛选 |
| `GET /api/products`、`/{id}` | 改造复用 | 分类体系商品列表和三级详情 |
| `GET /api/activities/enable`、`/{id}` | 兼容后改造 | 活动页和详情；新公开列表增加筛选 |
| `POST /api/signups` | 兼容后改造 | 普通活动报名，后续迁移到幂等动作接口 |
| `GET /api/inheritors`、`/{id}` | 必须先重构 | 改为公开脱敏 DTO 后供一级页使用 |
| `GET /api/news` | 保留 | 资讯作为二级内容和首页后置内容 |
| `/api/posts` | 保留兼容 | 种草能力下沉后继续使用，后续按既有设计迁移 `/api/notes` |

### 9.2 新增 API 建议

| 模块 | Method | 建议 URL | 核心返回/作用 |
|---|---|---|---|
| 产品体系 | GET | `/api/product-systems` | 六大体系、图片、说明、排序和启用状态 |
| 产品体系内容 | GET | `/api/product-systems/{code}/items` | 分页异构摘要，含 `targetType/targetId/actionType` |
| 服务体系 | GET | `/api/service-systems` | 公共服务类型及筛选项 |
| 传承人 | GET | `/api/inheritors` | 脱敏公开列表，支持地区/门类/级别/服务筛选 |
| 传承人 | GET | `/api/inheritors/{id}` | 公开详情、资质摘要、作品、商品、课程和服务 |
| 传承人作品 | GET | `/api/inheritors/{id}/works` | 图文/视频作品分页 |
| 活动 | GET | `/api/activities` | 支持类型、城市、日期筛选，返回余量 |
| 演出 | GET | `/api/performances`、`/{id}` | 仅公开已发布演出；与管理 CRUD 分离 |
| B 端合作 | POST | `/api/cooperation-leads` | 幂等提交合作意向 |
| B 端合作 | GET | `/api/cooperation-leads/{leadNo}/status` | 可选；登录或验证后查询进度 |
| 个人中心 | GET | `/api/users/me/summary` | 订单、预约、收藏、咨询、消息摘要 |

### 9.3 API 兼容原则

1. 旧 API 在 C 端迁移完成前保留，禁止同时删除路由和页面。
2. 新产品体系接口与 `/api/heritage-categories` 并存，不做同路径替换。
3. 异构目录只返回展示摘要和跳转类型，购买、预约、报名仍调用各自领域 API。
4. B 端表单使用服务端身份/风控和幂等键，不接受客户端传入 userId 作为真实身份。
5. AI 点位不调用占位假接口，不返回伪造对话数据。

## 10. 管理后台影响

| 后台模块 | 当前能力 | 新版需要 |
|---|---|---|

## 12. AI 点位预留规则

新版文件描述了首页导航、Banner、产品体系、业务入口、传承人、分类、活动、商品详情和 B 端页面的 AI 形象位置。结合当前一期约束，推荐：

1. 设计稿和组件结构预留命名槽位，例如 `ai-slot-home-banner`、`ai-slot-inheritor-hero`，默认隐藏。
2. 路由和业务 DTO 可以预留通用 `extensionSlots` 或 `featureFlags`，但当前后端不下发可执行 AI 动作。
3. 不添加 AI 悬浮按钮、麦克风、对话弹窗、自动播报、数字人视频或长按 Tab 行为。
4. 不创建 AI 人物、音色、讲解稿或对话记录表。
5. 不在现有商品/项目数据中写入虚构 AI 配置 ID。
6. 未来 AI 立项后单独评估隐私授权、内容审核、语音采集、模型供应商、费用、超时降级和未成年人保护。

## 13. 需要甲方确认的设计问题

在数据库或 API 设计冻结前，至少确认：

1. 平台最终品牌名是当前“非遗科技人文生态平台”还是新版文件中的“无念万艺”。
2. 六大产品体系名称是否为最终固定文案，稳定编码由技术方定义还是甲方提供。
3. “非遗美食风物”既是当前非遗门类中的“非遗美食”，又是产品体系，是否允许普通地方风物进入该体系；资质和“非遗”标注规则是什么。
4. “康养陪伴服务”的服务范围、主体资质、履约模式、计费方式和风险边界。
5. “分类”页是否只展示六大产品体系，还是同时保留非遗门类筛选。
6. 当前非遗发现、知识库、资讯、社区/种草的最终入口位置和一期优先级。
7. 传承人 Tab 是否就是普通第三个 Tab；新版“中间 + 号长按 AI”与传承人 Tab 的视觉/交互冲突如何解决。
8. B 端合作表单是否必须登录；是否收集统一社会信用代码、附件、预算和发票需求。
9. “在线咨询”首版是表单、平台客服还是即时聊天。
10. 分类页中的活动、课程和演出是否统一展示，详情页是否保持三种不同业务对象。

## 14. 推荐实施顺序

总体顺序按甲方指定：**导航 → 首页 → 产品体系 → 分类 → 传承人 → 活动 → B 端 → 我的 → 三级详情 → AI 预留**。

每个业务阶段内部仍必须遵循“数据契约 → migration → 后端 Service/API → 管理后台 → 小程序 → 联调验收”，避免先画完页面再反复改字段。

### 第 1 步：导航

- 冻结五个 Tab 名称、图标、路由和旧路由兼容表。
- 只建立新路由契约/页面壳，不立即删除商城或非遗 Tab 的旧页面。
- 验收：五个目标路由都有明确页面负责人、数据来源和空状态；旧分享链接仍可访问。

### 第 2 步：首页

- 冻结首页模块顺序、核心入口数量和 B 端入口。
- 定义新版 `/api/home` DTO 的兼容扩展。
- 现有六大非遗分类先保留，产品体系数据未就绪前不得用假数据替换。
- 验收：首页所有动态模块由 API 返回，单区块为空不会白屏。

### 第 3 步：产品体系

- 甲方确认六大体系名称和边界。
- 设计 `product_system/service_system` 及映射 migration。
- 建立运营后台配置和公开查询 API。
- 验收：六个体系可独立启停、排序并挂接真实内容；heritage category 数据不变。

### 第 4 步：分类

- 新建分类一级页和异构目录 DTO。
- 文创/美食/器具复用商城；手作复用课程；演艺复用 performance；康养无数据时明确空状态。
- 分类页完成后再正式把第二个 Tab 从“非遗”切到“分类”。
- 验收：六体系跳转目标正确，商城旧路由仍可达。

### 第 5 步：传承人

- 先完成公开 DTO、安全查询、项目/作品/服务关系，再开发页面。
- 新建列表和详情路由，完成后切换第三个 Tab。
- 验收：筛选、详情和关联内容可用；任何响应不含身份证、原手机号或证件原路径。

### 第 6 步：活动

- 冻结活动类型枚举，补城市、日期筛选和报名窗口。
- 明确普通活动、课程和演出的聚合/跳转边界。
- 验收：现有报名功能不回归，名额和状态显示一致。

### 第 7 步：B 端

- 先建立合作线索数据模型、隐私和状态机，再开发介绍页/表单页。
- 同步建设后台线索处理，不交付只有前端表单而无人处理的死链。
- 验收：重复提交受控、敏感字段脱敏、线索可分派跟进。

### 第 8 步：我的

- 调整现有入口命名和分组，保留订单、报名、帖子、收藏、认证。
- 按确认结果增加咨询和消息。
- 验收：登录失效、空状态和旧记录入口正常。

### 第 9 步：三级详情

- 商品详情补 SKU/关联文化内容；传承人详情新建；活动详情增强；B 端合作表单完善。
- 只展示真实存在的字段，所有可选模块为空时隐藏。
- 验收：列表到详情、详情到交易/预约/表单的链路完整。

### 第 10 步：AI 预留

- 最后检查各指定页面是否留有不会影响当前布局的组件槽位和 feature key。
- 默认隐藏、无点击动作、无 API 调用。
- 验收：关闭 AI feature 时页面与当前业务完全一致，不出现不可用按钮。
